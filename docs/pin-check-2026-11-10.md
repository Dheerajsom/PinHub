# Pin check and price coverage (2026-11-10)

Branch `feature/code-pin-check`. Two changes: a new `/check` page that reads
firmware and checks every pin it uses against the board's record, and the
curated price list grown from 11 to 31 boards.

## Pin check (`/check`)

Paste code, pick a board, and get each pin the code uses with what the record
says about it. Everything runs in the browser; the code is never sent anywhere.
The draft is kept in `sessionStorage` (bounded to the 100,000-character input
limit on read and write) so a reload in the same tab keeps it.

### What it reads (`src/lib/code-check/scan.ts`)

Dialects are detected from imports and calls, or chosen by hand:

| Dialect | Pin calls recognised |
| --- | --- |
| Arduino | `pinMode`, `digitalWrite/Read`, `analogRead/Write`, `tone`, `pulseIn`, `shiftIn/Out`, `dacWrite`, `touchRead`, `ledcAttach*`, `digitalPinToInterrupt`, ESP32 `Wire.begin(sda, scl)`, `SPI.begin(sck, miso, mosi, ss)`, `SerialN.begin(baud, cfg, rx, tx)`, `setSDA/SCL/TX/RX/…`, `setPins`, `Servo.attach` (declared `Servo` objects only), `Adafruit_NeoPixel`, `DHT`, `OneWire`, `SoftwareSerial`, `LiquidCrystal` declarations |
| MicroPython | `Pin(n, mode)`, `Pin.cpu.A5`, `Pin.board.X`, `ADC`, `DAC`, `PWM`, `TouchPad`, `NeoPixel`, `DHT11/22`, `OneWire`, `Signal`, `I2C/SPI/UART` with keyword pins (and by id alone, resolved to the record's default pins), `SoftI2C/SoftSPI` |
| CircuitPython | `board.X` in `DigitalInOut`, `AnalogIn/Out`, `PWMOut`, `TouchIn`, `NeoPixel`, `busio.I2C(scl, sda)`, `SPI`, `UART`, and `.direction` / `switch_to_*` |
| Raspberry Pi Python | `RPi.GPIO` (BCM, and physical pins under `GPIO.setmode(GPIO.BOARD)`), `gpiozero` devices including `"BOARD11"` / `"GPIO17"` strings and keyword pins, `lgpio` |
| Pico SDK | `gpio_init`, `gpio_set_dir`, `gpio_put/get`, pulls, IRQs, `gpio_set_function`, `adc_gpio_init`, `pwm_gpio_to_*` |
| ESP-IDF | `gpio_*` calls, `GPIO_NUM_n`, `uart_set_pin`, struct fields (`.sda_io_num`, `.gpio_num`, …), `pin_bit_mask` bits |

Comments, docstrings and string contents are masked before calls are read.
Simple constants are followed (`#define`, typed `const`/`constexpr`
declarations, Python module assignments, up to eight hops). A value the
scanner cannot follow (`pins[i]`, a function parameter) is listed for a hand
check, never guessed.

### What it says (`src/lib/code-check/check.ts`)

Only record-backed findings:

- **Fix:** power or ground pin used as a signal; output-type use of an
  `input-only` pin; any use of a `module-memory` (flash/PSRAM) pin; a
  `reserved` pin; analog read or write with no ADC/DAC function recorded;
  ADC2 (`adc-unavailable-with-wifi`) read when the code starts Wi-Fi; a
  MicroPython bus id that names a different controller than the pin carries on
  a fixed-mux chip (`I2C(0, sda=Pin(2))` on a Pico is I2C1).
- **Check:** strapping, boot and USB-serial pins (each quoting the board's
  source note); PWM or a hardware bus signal not recorded on the pin; ADC2
  without Wi-Fi in the code; one pin used for two functions.
- **Note:** JTAG pins and the onboard LED.

Bare numbers resolve the way the toolchain numbers pins: the board's recorded
Arduino numbers (with `analogRead(0)` as A0), otherwise GPIO numbers, and
physical header positions under `GPIO.BOARD` on a Raspberry Pi. When an
Arduino sketch runs on a board whose record names no Arduino numbers (ESP32,
RP2040), the report says GPIO numbers were assumed. Names (`A0`, `D13`,
`PA5`, `GP15`, `board.SDA`) match the SDK name, the Arduino name, the label
parts and the aliases. `LED_BUILTIN`, `Pin("LED")` and `board.LED` resolve to
the pin flagged `onboard-led`, or report that none is on the header.

The page offers the 126 boards whose records carry chip pin names
(`pinFunctions`); it says so when a search finds none.

### Hand-offs

- **Open in planner** writes the pins as planner claims (`use=` keys), named
  by the constant the code used or by the use.
- **Copy report** writes Markdown with every table cell escaped and control
  characters removed.

## Prices: 31 boards

Added 20 curated listings, each read through the production parser
(`npm run refresh-prices`: 31 checked, 0 failed, 2026-11-10 22:07 UTC):

- Adafruit: Raspberry Pi 4 Model B 4 GB (4296), Pi 3 B+ (3775), Pi Zero W
  (3400), Pi 400 (4795), micro:bit v2 (4781), ESP32-C3-DevKitM-1 (5337), QT Py
  RP2040 (4900), Feather M4 Express (3857), Feather ESP32 V2 (5400), ESP32-S3
  Feather (5477).
- Arduino store: UNO Rev3, Nano, Mega 2560 Rev3, Nano Every, Leonardo, Nano 33
  IoT, Nano RP2040 Connect, Nano 33 BLE Sense Rev2, Micro, MKR WiFi 1010.

The original 11 bundled observations are unchanged (the hourly job keeps the
shared store current); the new ones carry their real check time. The price
tests now set their clocks just after the newest bundled check instead of a
fixed September date, so adding a listing cannot make the fixture look like it
is in the future.

Not added: Teensy 4.1 (Adafruit lists it as discontinued), Adafruit's "ESP32
Development Board – Developer Edition" (the page does not name the DevKitC
revision, so it cannot be tied to `esp32-devkitc` with confidence), and
boards sold only by stores the price checker cannot read (STM32 Nucleo, Seeed
XIAO, PJRC).

## Known limits

- The scanner reads code statically. Pins chosen at run time, passed through
  functions, or built in loops are listed as not followed.
- Library coverage is the common set above; an unrecognised library call is
  silently skipped, not reported.
- Arduino numbering on boards without recorded Arduino names assumes GPIO
  numbering; Arduino cores that renumber (for example Nano ESP32 in its
  default "by Arduino pin" mode) are not modelled beyond what the record says.
- Hints at the end of very long lines can sit past the textarea's horizontal
  scroll range.
- Live-store prices for the 20 new listings appear after the first hourly run
  on `main` once this is merged.
